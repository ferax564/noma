# Noma: Application Review and the Road to "the Next Confluence"

**Date:** 2026-09-22 · **Baseline:** `main` @ `abb833e` (v0.17.0 + enterprise kernel) · **Branch:** `claude/app-review-confluence-c97f9l`

This review covers the whole repository. It looks at the core format engine, Noma Cloud (the hosted workspace), the enterprise modules, and the tests and CI. It asks one question: **what stands between Noma and being a credible Confluence replacement?** Some fixes landed on this branch. Everything else is written up as a prioritised roadmap.

---

## 1. Verdict

Noma has something Confluence does not have and cannot easily copy. Its source of truth is plain text. Every block has a stable ID that agents can patch safely. Edits are proofed, hash-checked and approved by a person. The AI features are built around citations. That combination is the right wedge for an **agent-native team wiki**.

The product around that core is not yet a Confluence replacement. There are three reasons:

1. **Security was not production-grade.** Two critical and three high-severity authorization bugs were found. All five are fixed on this branch (§3).
2. **Wiki basics were missing.** There was no page tree, no labels, no way to watch a page and no visual diff between versions. These are now built (§4). Attachments and a real WYSIWYG editor are still missing, and they block adoption.
3. **Scope has sprawled.** Cloud, enterprise and PaperDOM code make up about 40% of `src/`, even though CLAUDE.md lists them as out of scope. Some enterprise modules are demo-grade. There is a large surface area to maintain and not much depth where users actually spend their time: editing, navigating and finding pages.

**Recommendation:** freeze the enterprise surface. Spend the next two releases on the editor, attachments and the core wiki. Market Noma as *"the wiki your agents can safely edit"*, not as a feature-for-feature Confluence clone.

## 3. Security

### 3.1 Fixed on this branch

| # | Sev. | Finding | Fix |
|---|---|---|---|
| S1 | **Critical** | **Any user could become workspace admin.** `requireWorkspaceOwner` let in anyone who owned *any* space, or who was first in the user list sorted by *name*. Registering as `"!"` or creating a space was enough to set enterprise policy, run a retention wipe, enforce SSO and edit SCIM. | Admin is now the `NOMA_CLOUD_ADMIN_USER_IDS` allowlist. If that is unset, it is the first user ever registered (by insertion order). |
| S2 | **Critical** (SSO deployments) | **SCIM rebinding allowed account takeover.** An upsert could map an attacker's IdP subject to the admin's `userId`. `/api/auth/sso` would then issue the admin's token. | An `externalId` or `userId` already bound to one identity cannot be claimed by another, and an existing identity cannot be rebound. `userId` must exist. |
| S3 | High | **An editor could escalate to page owner through a space.** Bob, an editor on Alice's page, could create his own space containing that page and inherit `owner` on it. | Adding a page to a space now requires `owner` on that page. |
| S4 | High | **Agent grants outlived the human's access.** `list_ids`, `proof` and `proposal` checked only the agent's grant, so a removed user's agent could still read and propose changes. | Every agent grant is capped by the agent owner's *current* role on the document. |
| S5 | High | **Stored XSS through `javascript:` links.** `[x](javascript:…)`, `::button{href}`, `::dataset{src}` and citation URLs were rendered as live links on same-origin `/d/` pages, where the user token sits in `localStorage`. | Added `safeHref()` across all href sinks. Artifact responses now also carry CSP `sandbox allow-scripts allow-popups`, which gives them an opaque origin. |
| S6 | Medium | **Server file read through patch proofs.** `::dataset{src="<id>.json"}` inlined legacy JSON records from the data directory into the proof preview. | Added `ProofOptions.inlineSources`. The Cloud passes `false`. |
| S7 | Low | Trust `verifiedBy` could be forged. `/d/%E0` returned a 500. | `verifiedBy` is now always the caller, and malformed paths return 400. |

Regression tests cover S1–S3, S5 and S7, in `test/cloud-server.test.ts` and `test/renderer-html-url-safety.test.ts`.

### 3.2 Still open (recommended next)

- **Gate-token brute force.** `/cloud?access=<guess>` is outside the `/api/` rate limiter. Apply the auth limiter to every request that carries `access=`.
- **Unbounded per-request work.** `knowledgeDocuments` parses up to 10k documents on every call. Platform `list()` scans every record of a kind. Offline drafts and analytics have no per-user caps. Add pagination, caching keyed by content hash, and quotas.
- **Token fragment exposure.** `publicUser.tokenPreview`, the last 6 characters of each user's token, is visible to every user through `/api/users` and `/api/db/query`. Show it only to its owner.
- **Backup import is not atomic.** It writes documents one by one and can stop halfway, and it reveals whether a document ID exists. Validate everything first, then write inside one transaction.
- **Legacy JSON is left in `dataDir` after SQLite import.** Move or delete it once the import succeeds.
- **Auth tokens live in `localStorage`**, and the Yjs socket takes its token in the query string. Move to HttpOnly session cookies with CSRF protection before any SaaS offering.
- **Only one long-lived bearer token per user.** Add named, scoped, revocable personal access tokens (Confluence has these), with expiry.

## 5. Code-health findings (core engine)

Each of these was reproduced with a small script. They are ordered by user impact.

**Parser (`src/parser.ts`)**

1. **Quoted attribute values are coerced to numbers.** `::claim{id="2024"}` makes `id` the number 2024, so the block loses its ID. `version="1.10"` becomes `1.1`. Only unquoted values should be coerced.
2. **Invalid YAML frontmatter throws** instead of producing a best-effort tree. This violates Iron Rule 3.
3. **A document that starts with `---` as a thematic break can lose content.** The first paragraph is read as frontmatter.
4. **Non-Latin headings get empty or odd slugs.** `# 日本語` gets `""`, `## Привет` gets `"-2"`. This matters for i18n wikis.
5. **A trailing `{…}` in a heading is always read as attributes.** `# Set {a, b}` loses its braces.
6. **Only backtick fences with a word-only info string are recognised.** ```` ```c++ ````, `~~~` and four-backtick fences don't suppress structure parsing.

**Patch engine (`src/patch.ts`)**

1. **Attribute values containing both `'` and `"` serialise with `\"`**, which the parser cannot read, and this corrupts the attributes.
2. **Newlines in attribute values or keys, and `::` lines in `replace_body` content, can inject structure.** An agent patch can create or close blocks outside its target. This undermines the block-level safety promise and should be rejected in `validateOpShape`.
3. **`replace_body` on an unclosed directive keeps the old body.** On a list item it drops the `{#id}` marker.
4. **CRLF files end up with mixed line endings** after `update_attribute`.

**Architecture**

- `src/index.ts` re-exports the Cloud and enterprise modules, so `import { parse }` loads `better-sqlite3` (a native module), `ws` and `yjs`. Split this into a lean `@ferax564/noma` core and a separate `@ferax564/noma-cloud`, or use subpath exports.
- `puppeteer` is a devDependency, but `--to pdf` imports it at runtime, so it breaks for npm installs. Make it an optional peer dependency.
- There are two full patch engines, one on the AST (`apply*`) and one on source (`applySrc*`). `patchSource` is canonical, so plan to retire the AST path.
- Monoliths to split: `cloud-server.ts` (4.6k lines, about 40 `route*` functions), `renderer-docx.ts` (4.5k), `patch.ts` (3.4k), `docx-review-sync.ts` (3.3k).
- The `packages/{document-core,work,platform,…}` "extraction boundaries" are one-line re-exports of the whole CLI. They add no isolation.
- The `web/` bundles are not typechecked in CI. `tsconfig` only includes `src/`. At baseline `web/cloud-app.ts` had 13 type errors, one of them a real runtime `ReferenceError` (`focusBlock`), now fixed. Add a `tsconfig.web.json` to CI.

**Tests and CI**

- PR CI does not run `build:site` or `render:examples`, so Iron Rule 5 ("examples are tests") is only enforced after merge.
- There are no fuzz or property tests for the round trip parse → `renderNoma` → parse. Every parser and patch bug above is the kind a fuzzer finds within minutes.
- Before this branch there was no HTML-renderer escaping or URL-safety test file. One now exists.

## 6. Enterprise modules: real vs. demo

| Module | Reality |
|---|---|
| `enterprise-yjs` | A working persist-before-ack relay. Rooms are never evicted and updates never compacted, so memory is unbounded. It has a `MAX(seq)+1` race across processes, test hooks in production code, and no presence. |
| `enterprise-crdt` | **Not a CRDT.** It parses, mutates the AST and re-serialises with `renderNoma`, which bypasses the source-preserving `patchSource`. Rename it or replace it. |
| `enterprise-atlassian` | A real thin REST client with 429 retry. It has no pagination (`maxResults: 50`), and its Cloud and Data Center branches are identical. |
| `enterprise-aws` | A static CloudFormation object that would not deploy: `DBInstance` is missing its class, storage and username. |

These modules are fine as design spikes. They should not be described as shipped capabilities (`docs/enterprise.noma`, README) until they are hardened.

## 7. Roadmap: "the wiki your agents can safely edit"

### Phase 1: Trustworthy core (next release, about 4 weeks)

- Close the remaining items in §3.2, especially cookie sessions, scoped PATs and rate limiting on `access=`.
- Fix parser bugs 1–4 and patch bugs 1–2 from §5. Add a parse/patch fuzz suite to CI.
- Split the npm package into core and cloud. Typecheck `web/` in CI, and run `build:site` on PRs.
- Keep the shipped wiki basics solid: add drag-and-drop in the tree, label filters in search, and email digests for watchers.

### Phase 2: Editor and content (about 6–8 weeks). This is what decides adoption.

- **A block editor that keeps the stable IDs.** The enterprise shell already has a TipTap/Yjs spike. Promote it into Cloud as the default editor, bound to `.noma` blocks. Each paragraph or block keeps its ID, and source mode stays one click away. Include slash commands for the Noma directives (claim, decision, callout, table, mermaid, math).
- **Attachments:** content-addressed blob storage (local disk, then S3), `::figure{src="att:<hash>"}`, drag-and-drop and paste upload, and per-space quotas.
- **Live co-editing and presence** in Cloud, using the Yjs relay once room eviction and compaction exist.
- **Page restrictions:** a deny or restrict list at page level, on top of the additive grants.
- **Macros:** children display, include/excerpt (transclusion by block ID, which is a natural fit for Noma), and an embedded issue macro backed by the existing tracker.

### Phase 3: Migration and ecosystem

- **One-click Confluence import** in Cloud, reusing `enterprise-atlassian` plus the storage-format adapter. Keep page tree, labels, attachments, comments and permissions. This is the lever that makes people switch.
- Outbound webhooks, a Slack or Teams notifier, and a Jira link macro.
- User and space templates and blueprints, with variables.
- Export PDF and DOCX from Cloud; the renderers already exist.

### Phase 4: Where Noma beats Confluence

- **Generative AI on the trust loop.** Summarise, draft and "update this page from source X" all go through proof → human approval → hash-checked apply, with block-level citations. Confluence's Rovo cannot offer per-block provenance.
- **Stale-knowledge maintenance.** Trust and freshness metadata plus recipes, so agents find and propose fixes for outdated pages.
- **Git-native spaces.** Two-way sync of a space with a repository of `.noma` files. Docs-as-code teams keep their workflow and business users get the wiki.

### Explicit non-goals for now

- More enterprise surface (AWS templates, pilots, extra PaperDOM features) until Phases 1–2 ship.
- Feature-for-feature Confluence parity: whiteboards, databases, a marketplace.

## 8. Decisions needed from the maintainer

1. **Positioning.** Is Noma a *format with a reference host* or a *hosted wiki product*? The roadmap assumes the latter. If it's the former, most of Phase 2 moves to partners.
2. **CLAUDE.md scope list.** "What NOT to do" forbids a cloud platform, WYSIWYG and realtime collaboration, but the repo ships all three. Either update the list or move Cloud and enterprise into their own repository or package.
3. **Admin bootstrap.** Is "first registered user" acceptable, or should production require `NOMA_CLOUD_ADMIN_USER_IDS` and fail closed? Fail-closed is recommended for production.
